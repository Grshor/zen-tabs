# zen-tabs — разбор вкладок локальной моделью

Раскладывает открытые вкладки Zen (Firefox) по смысловым группам. Ничего не уходит в интернет:
запрос идёт на локальный сервер `127.0.0.1:8091` (проект [localmix](../localmix)).

Замер на живых данных: **689 вкладок → 12 групп за 20 секунд**, ни одна вкладка не потеряна.
Шесть вкладок модель разбирает за 0.2 с (315 токенов на вход, 28 на выход).

## Установка в Zen

1. `about:debugging#/runtime/this-firefox` → **Load Temporary Add-on** → выбрать
   `extension/manifest.json`.
2. Иконка появится на панели; расширение живёт до перезапуска браузера.

Постоянная установка требует либо подписи (AMO), либо `xpinstall.signatures.required=false`
в `about:config` — по умолчанию эта настройка не выставлена, и Zen, как Firefox Release,
неподписанные дополнения не ставит. Для личного инструмента временного варианта достаточно.

## Как пользоваться

Три кнопки в попапе:

- **Разобрать по смыслу** — локальная модель даёт каждой вкладке категорию из короткого списка
  (код, документы, учёба, видео, музыка, игры, покупки, переписка, соцсети, новости, поиск, разное).
  Список категорий общий для всех вкладок, поэтому большие наборы не разваливаются на
  «код / работа с кодом / Документы и код» при разборе по частям.
- **По доменам** — мгновенно, без модели: группирует по сайту. Хорошо работает там, где
  смысловая модель ошибается.
- **Применить** — создаёт настоящие группы Zen (`tabs.group` + `tabGroups.update`) с именами и цветами.

Дубликаты (одна страница с разными `utm`-хвостами) показываются отдельно, лишние закрываются
кнопкой. Вкладку с такой же страницей, но активную, и закреплённые — не трогает.

**Закреплённые вкладки исключаются из применения**: Firefox при группировке их принудительно
открепляет, а это уже потеря состояния.

## План пространств (глобальная раскладка)

Задача: разложить **все** вкладки по 9 пространствам, максимально разным по смыслу, и
внутри каждого — по подтемам. (Сначала их было 8: «наука и мышление» на 144 вкладки
разрезано на «наука и ИИ» и «философия и мышление» — в одном пространстве жили два
разных смысла.). Расширение этого не умеет и не сможет: Zen отдаёт расширению
вкладки только активного пространства, а сменить вкладке пространство можно лишь внутренним
(привилегированным) `moveTabToWorkspace`. Поэтому планирует отдельная программа, а применяет
расширение — режимом «очередь переносов» (B).

```bash
lm plan-model          # поднять модель планирования (4B, CPU, порт 8094) — VRAM не трогает
lm plan                # посчитать план и раздать его на 127.0.0.1:8093
lm plan-show           # короткая сводка готового плана
```

Прямой запуск: `bun bin/assign.mjs --model 8094` (таблица), `--json` (машинно-читаемо),
`--sample` (40 вкладок для проверки гипотез), `--limit N`, `--no-subtopics`.

### Как принимаются решения

1. **Инвентарь** — все вкладки всех пространств из `zen-sessions.jsonlz4`: заголовок, адрес,
   текущее пространство, закрепление, время последней активности.
2. **Пространство вкладки** — модель выбирает одну из 9 тем. В промпте: имя, описание и
   **4 примера заголовков из твоих же вкладок** этого пространства. Это решающая деталь:
   без примеров согласие с твоей раскладкой было 57 %, с примерами — заметно выше.
   Ответ «0» = «не понял» → вкладка остаётся там, где была.
3. **Подтемы внутри пространства** — в два шага: сначала модель предлагает 4–6 подтем по
   примерам вкладок пространства, потом раскладывает вкладки по номерам этих подтем.
   Одним шагом нельзя: на 13 вкладок bevy модель выдала 13 разных ярлыков
   («бэви-формы», «бэви-сохран», …) — свободные ярлыки не склеиваются.
4. **План-диф** — по каждому пространству: сколько приезжает и откуда; по каждому исходному:
   сколько уезжает. Вкладки не закрываются вообще: перенос = открыть в целевом пространстве
   и закрыть исходную.

### Замер на живых данных (24.09.2026)

| модель | согласие с твоей раскладкой | скорость |
|---|---|---|
| MiniCPM5-2B Q4 (:8091, GPU) | 44 % | 2.9 с на 40 вкладок |
| Qwen3.5-4B Q4 (:8094, CPU) | 68 % | 43 с на 40 вкладок |

Поэтому планировщик по умолчанию считается 4B. «Согласие» — доля вкладок, которым модель
назначила то же пространство, где они лежат у тебя (по 17 пространствам, у которых есть
однозначная целевая тема). Модель намеренно поднимается **на CPU**: на карте уже живут
два сервера и игра, и вытеснять их ради батча незачем.

Ключевое наблюдение по данным: **youtube.com — 292 вкладки (43 %), и они размазаны по 17
пространствам**; поиск и github — по 14 и 10. То есть по домену раскладывать нечего,
решает смысл заголовка — поэтому и нужна модель с примерами, а не правила по хостам.

### Режим применения B (очередь переносов)

Расширение читает план с `http://127.0.0.1:8093/plan.json` и работает по активному
пространству: «открыть здесь N вкладок, которые должны жить тут» и «закрыть N вкладок,
которые уже открыты в своих новых пространствах». Порядок фиксированный — сначала открыть
в целевом, потом закрыть в исходном; иначе вкладки потеряются.

## Командная строка (без браузера)

```bash
BUN=~/.local/share/mise/installs/bun/1.4.2/bin/bun   # если шим bun не настроен: mise use -g bun@1.4.2

$BUN bin/session.mjs             # открытые вкладки из хранилища сессий Zen (mozlz4, без зависимостей)
$BUN bin/plan.mjs                # разбор моделью
$BUN bin/plan.mjs --domain       # разбор по доменам
$BUN bin/plan.mjs --json         # машинно-читаемый план
$BUN test/smoke.mjs              # проверки ядра + живой прогон на настоящих вкладках
```

`bin/session.mjs` читает `sessionstore-backups/recovery.jsonlz4` самого свежего профиля —
это даёт доступ к текущим вкладкам без браузера, тем же кодом, что вызывает расширение.

## Проверка в браузере

```bash
$BUN bin/make-chrome.mjs         # собирает .build/chrome и печатает ID расширения
```

Собранный вариант запускается в Chromium с `--load-extension` — на нём проверялся весь путь
(создание вкладок → разбор моделью → применение групп). Firefox-версия отличается только
манифестом: `manifest.json` (MV2) против `manifest.chrome.json` (MV3).

## Что внутри

| файл | роль |
|---|---|
| `extension/core.js` | вся логика: промпты, разбор ответа, категории, дубликаты, план. Грузится и как `<script>`, и через `require()` |
| `extension/popup.*` | попап: список групп, чекбоксы, применение |
| `bin/session.mjs` | чтение сессий Zen (mozlz4 + LZ4-блок на чистом JS) |
| `bin/plan.mjs` | CLI-план для OMP и отладки |
| `bin/make-chrome.mjs` | сборка Chromium-варианта для проверки |

## Ограничения, честно

- Модель — MiniCPM5-2B. Она уверенно раскладывает видео/покупки/код, но путает близкие
  категории: на большом наборе в «Соцсети» попадали ссылки на GitHub. План — **предложение**:
  применить можно выбранные группы, а не все сразу.
- Группировка переставляет вкладки: они становятся смежными блоками (требование API).
- Категорий ровно столько, сколько в списке; «умных» названий групп модель не придумывает
  (это плата за устойчивость на 689 вкладках).
- Порог: если модель отвечает мусором на чанк, вкладки просто остаются вне групп,
  а ошибка показывается в статусе.
